# 新颖性判决实验规格（Go/No-Go 门禁 G0）

> 目的：**在投入半年之前，用 2 周验证核心主张是否成立。**
> 来源：`../docs/PAPER_PLAN_SCI_Q1.md` §2.3、`../docs/GRADUATION_TIMELINE.md` §4 事项二。
> 优先级：**P0 — 不做这一步，后续所有工作都是赌博。**

## 1. 待验证的主张

> **C1 / C2**：在结构化文档抽取任务中，把对抗协议的反证媒介从**自然语言论证**改为
> **机器可核查的证据定位符**，能显著提升幻觉的修正率。

**判决问题**：能否写出「我与 X 的差异是 Y，且 Y 有实验支撑」？

## 2. 实验设计（两臂对照）

**核心原则：只有「反馈形态」这一个变量不同，其余全部相同。**

| | **Arm A（对照）** | **Arm B（处理）** |
|---|---|---|
| 反馈形态 | **自然语言反证** | **locator 反证** |
| 反馈内容 | 验证者的措辞，如「你抽的数量似乎不对，请重新核对原文」 | 「工作表 sheet1 第 5 行第 3 列：原文为 `100`」 |
| 是否含 locator | ❌ | ✅ |
| 是否含原文值 | ❌ | ✅ |
| 是否含措辞 | ✅ | ❌（按 C1 设计，措辞必须剔除） |
| 其余条件 | 同模型、同提示词骨架、同重试次数、同温度、同随机种子 | 同左 |

### 样本构造（推荐方案：**人工注入错误**）

> 比「从真实运行中捞错误样本」更干净——两臂面对**完全相同**的错误与证据，内部效度高。

1. 从自建制造业订单集取 **50 个**订单，每个订单挑 **1 个字段**（数量 / 单价 / 交期 / 物料号）
2. 对该字段**注入一个错误值**（如把 `100` 改成 `1000`），记录：`订单ID / 字段名 / 错误值 / 正确值 / locator`
3. 构造一条合法的 `CHALLENGE` 消息，其 `evidence` 携带**正确的 locator 与原文真实值**
4. 分别用 Arm A 与 Arm B 的反馈形态触发一次重试
5. 判定重试输出中该字段是否被修正为正确值

**对照方案（备选）**：直接使用 `evaluation/results/baseline_generated_complex_test_20260910_234250`
（240 样本）与 `cord_v2_test_20260911_012942` 中真实产生的挑战，筛选出有可复现反证的字段。
**缺点**：两臂的错误难度不可控，噪声更大。**建议先用注入方案。**

---

## 3. 指标定义

| 指标 | 定义 | 角色 |
|---|---|---|
| **幻觉修正率**（correction rate） | 重试后被修正为正确值的字段数 / 被挑战字段总数 | **主指标** |
| 过度修正率 | 从错误值改成**另一个错误值**的比例 | 次要 |
| 弃权率 | 修正后变为 `null` 的比例（放弃核对、直接弃权） | 次要（**Arm A 若显著更高，正是 C1 的机制证据**） |
| 平均 token 消耗 | 两臂应基本相同，作为「同预算」的对照证明 | 对照 |

## 4. 最小代码改动方案

> 改动量小，且**默认行为不变**（新增参数默认值 = 现有行为），不影响 `paper-v1-baseline` 的语义。

### 4.1 扩展反馈构造函数（已实现）

**文件**：`application/protocol/adversarial.py`
**函数**：`build_counter_evidence_feedback(challenges, *, mode="locator")`

```python
FEEDBACK_MODES = ("locator", "natural_language")
```

- `mode="locator"` → **Arm B**，与加入 `mode` 之前逐字节相同（默认值即线上行为）
- `mode="natural_language"` → **Arm A**，跳过 evidence 循环，只输出验证者措辞

**⚠️ 实现时发现的关键点（原规格写错了，已修正）**

原规格写的是「`mode="natural_language"` → 只输出 `message.payload["reason"]`」。但真实
验证者生成的 `reason` **本身就内嵌了 locator 与原文值**：

```
第 3 项 quantity 与工作表 采购订单 第 17 行对应列不一致：原单元格为 100，抽取为 98765。
```

直接回灌 `reason` 会让 Arm A 也拿到坐标和真值，**单变量对照当场失效**。因此 Arm A 的
措辞改为由 `subject`（`item[i]` + `field`）重新构造：

```
第 3 项的 quantity 与原文不一致，请重新核对原订单。
```

**这一条本身就是论文素材**：它说明「现有协议里措辞与证据是混在一起的」，这正是 C1
主张要拆开的东西。

**`item_index` 是否算 locator —— 唯一需要人工拍板的边界（见 D13）**

Arm A 保留了「第几项」。理由是 `item_index` 指向**主张列表**而非源文档坐标，一个纯自然
语言的验证者也必然会说「第 3 项的数量不对」。但 Excel 里「第 i 项」几乎等价于「第 i 行」，
所以这是一处口径选择，不是客观事实。若审稿人质疑，需补跑一版**完全不给项号**的
Arm A'（措辞退化为「有字段与原文不一致」）作为稳健性检验。

**已实现的两处稳健性设计**

| 设计 | 原因 |
|---|---|
| **字段均衡分配**（选当前用得最少的字段） | 自建订单集明细表**没有交期列**（只有 物料名/规格/数量/单位/单价）。固定轮转会让 `delivery_date` 整类落空、`material_name` 垄断样本。改为均衡分配后 50 条样本分布为 13/13/12/12。 |
| **判定口径复用 `GroundingVerifier._cell_matches`** | 让「修正率」严格等于验证者会接受的比例，而不是脚本自己另立一套数值/日期/文本比较规则。 |

**错误注入方式**（贴近真实失效模式，而非随机字符串）

- 数值字段（`quantity` / `unit_price`）：十进制位错位，`100 → 1000`
- 文本字段（`material_name` / `specification`）：换成**同一张订单里另一个真实存在**的取值，
  制造「张冠李戴」型误读

**判定分类**（比原规格多两档，便于诊断机制）

`corrected`（改对）/ `abstained`（改判 null，弃权）/ `unchanged`（原样保留错值）/
`other_wrong`（换成另一个错值，过度修正）/ `error`（调用失败）

## 7. 已知陷阱与风险

| 陷阱 | 说明 | 规避 |
|---|---|---|
| **提示词泄漏** | Arm A 的自然语言反馈若不小心带上 locator 格式，两臂就不再是单变量对照 | 实现后先做**单元测试**断言：Arm A 的输出中不含 locator 与原文值 |
| **错误难度不均** | 若用真实运行捞样本，两臂面对的错误难度不可比 | 优先用**人工注入**方案 |
| **模型记忆** | 同一订单跑两次，第二次可能因上下文记忆而「修正」 | 每臂独立会话，不共享历史 |
| **`feedback` 未生效** | 文本路径的 `{feedback}` 依赖 `ChatPromptTemplate` 变量填充 | 跑通后先抽查 1 条，确认反馈文本确实进入 prompt |
| **样本量不足** | n=50 对中等效应量的检验力偏低 | 效果接近临界时扩到 100 |
| **成本失控** | 两臂 × 50 样本 × 3 重复 = 300 次调用 | 规模很小；先用 8B 级模型打通 |

| 弃权率 | 0.0 | 0.0 |

### 11.2 诊断：不是机制无效，是任务太容易

n=5 **不足以判决**，但两臂同时饱和到 100% 是一个必须正视的信号。根因在**注入难度**：

`inject_wrong_value()` 当前只造两种错误（`scripts/novelty_experiment.py:112`）：

| 字段类型 | 注入方式 | 可定位性 |
|---|---|---|
| 数值（quantity / unit_price） | **×10**（`100 → 1000`） | 量级错得离谱，肉眼可辨 |
| 文本（material_name / specification） | 换成同单**另一个真实值** | 张冠李戴，但单内候选很少 |

两类错误的共同点是：**"哪个值错了"这件事本身不需要定位符就能知道**。
Arm A 的措辞「第 6 项的 quantity 与原文不一致，请重新核对原订单」已经给出了
「哪一项 + 哪个字段」，模型只需重读那一行——**locator 提供的「哪一格」是冗余信息**。

> 换句话说：当前实验测的是「模型能否重读一个它本来就看得见的单元格」，
> 而不是「locator 这个媒介是否降低了幻觉修正的成本」。

### 11.3 若就这么跑完 300 次，会得到什么

一个 Δ=0 的 NO_GO。而这个 NO_GO **无法区分两种解释**：

1. 机制真的没用（C1 被证伪）→ 该砍
2. 任务难度低于区分阈值（设计缺陷）→ 该改难度重跑

用 3.7 小时换一个不可解释的结果，是 G0 门禁本该拦住的事。

### 11.4 修复方案：难度阶梯（D19）

把注入从「粗错」升级为「**同行同列的另一个真实值**」，让错误在**数值上完全合法**：

| | 当前（gross） | 建议（subtle） |
|---|---|---|
| 数值字段 | `100 → 1000`（量级错位） | 换成**同列另一行**的真实值，如第 5 项取第 6 项的数量 |
| 文本字段 | 同单另一真实值 | 保持不变（已是该形态） |
| 为什么难 | 值本身很假 | 值完全合法；**只有回到正确的那一格才能发现** |
| locator 的增量 | 无（冗余） | **有**——它把「重读整张表」缩成「核对第 17 行第 5 列」 |

**为什么这是更强的设计**：它精确复现了真实失效模式（**行错位 / 张冠李戴**），
而这正是制造业订单抽取最典型的错误。同时它保持单变量——两臂仍只差反馈形态。

**实现代价**：约 8 行——`inject_wrong_value` 的数值分支改为「从同列其他行取一个
不等于 gold 的真实值」，复用文本分支已有的 `alternatives` 逻辑。

**✅ 已实现（2026-10-02）**：新增 `--difficulty {gross,subtle}` 与三个辅助函数
（`_alternatives_in_column` / `_common_prefix_length` / `_most_similar`）。
`subtle` 档不是随机取同列值，而是**优先取与 gold 最相似的候选**（最长公共前缀），
最大化混淆度。实测效果：

| 字段 | gold | subtle 注入 | 差异 |
|---|---|---|---|
| specification | `CJX2-2510 AC220V 11` | `CJX2-1210 AC220V 22` | **只差四位数字** |
| unit_price | `0.38` | `0.33` | 只差一位 |
| unit_price | `14.24` | `154.25` | 同列真实值 |
| material_name | `屏蔽控制电缆` | `同步带轮` | 张冠李戴 |

> **⚠️ 实现时发现并修掉的对照缺陷（方法论上很重要）**：
> 最初 `inject_wrong_value` 与「选目标行」**共用同一条随机流**。`gross` 的文本分支
> 多消耗一次 `rng.choice`，导致后续订单的目标行整体漂移——**两档跑出来根本不是同一批
> 样本**（第 4 条起 `sample_id` 就对不上）。这样「难度」与「样本身份」两个变量混淆，
> 阶梯实验失去意义。
>
> **修复**：注入改用**由样本身份派生的独立随机源**
> （`_injection_rng(order_stem, item_index, field)`），并在 `build_sample` 里加
> **统一种子条件**（样本必须在两档下都可注入）。实测两档 `sample_id` / `locator` /
> `gold_value` 逐一相同。守卫测试：
> `tests/test_novelty_experiment.py::DifficultyIsolatesTheSampleIdentityTests`。

> ⚠️ **副作用**：升级后修正率会**整体下降**（两臂都降）。这是预期的——
> 我们要看的是 **Δ** 是否随难度上升而变大，而不是绝对修正率。
> 建议**两档都跑**（gross 作对照、subtle 作处理），这样论文里可以给出
> 「locator 的收益随错误可定位性下降而单调上升」的**趋势证据**，比单点对照更有说服力。

## 12. 难度阶梯预实验结论：注入范式本身无法区分两臂（2026-10-02）

### 12.1 实测结果：两档 × 两臂 = 四个格子全部饱和

| 注入难度 | 臂 | 修正率 | 弃权率 | 未改变率 | 平均 tokens | 平均延迟 |
|---|---|---|---|---|---|---|
| **gross** | A_natural_language | **1.00** | 0.00 | 0.00 | 5,631 | 43.9 s |
| **gross** | B_locator | **1.00** | 0.00 | 0.00 | 5,665 | 43.4 s |
| **subtle** | A_natural_language | **1.00** | 0.00 | 0.00 | 5,631 | 44.1 s |
| **subtle** | B_locator | **1.00** | 0.00 | 0.00 | 5,690 | 44.0 s |

```
gross  : 20/20 corrected → NO_GO（Δ = +0.0000，p = 1.0000）
subtle : 20/20 corrected → NO_GO（Δ = +0.0000，p = 1.0000）
discordant (A错B对 / A对B错) = 0 / 0（两档都是）
```

产物：`evaluation/results/novelty_experiment_gross_20261002_011622/`、
`evaluation/results/novelty_experiment_subtle_20261002_013056/`

> **难度阶梯没有拉开任何差距。** 把错误值从「×10 量级错位」升级为「同列另一行的真实值
> （且与 gold 最相似）」后，两臂依然 100% 修正。

### 12.2 根因：模型根本没有幻觉可修

翻出基线评测（`evaluation/results/baseline_generated_complex_test_20260910_234250/`）：

| 字段 | 正确 / 总数 | 准确率 |
|---|---|---|
| quantity | 5882 / 5882 | **1.000** |
| unit_price | 5882 / 5882 | **1.000** |
| unit | 5882 / 5882 | 1.000 |
| order_number / customer_name / total_amount | 240 / 240 | 1.000 |
| material_name | 5869 / 5882 | 0.9978 |
| specification | 5838 / 5882 | 0.9925 |

**全库 29,410 个字段值中只有 57 个错误（0.19%）**，且全部集中在两个文本字段。

这就解释了一切：

1. **没有真实幻觉可修** → 只能靠人工注入造错误；
2. **任何注入的错误都能被「重读一遍」修正** → 因为模型重抽取的准确率接近 100%，
   与「反馈里有没有定位符」无关；
3. 因此 **Arm A 的措辞「第 i 项的 field 与原文不一致」已经足够**，locator 是冗余信息。

> **这不是难度调参能解决的问题**，而是「注入错误 + 强模型」这一组合的结构性缺陷。
> 把难度继续往上调，只会让错误值越来越不像真的，而模型依然能靠重读改对。

### 12.3 对 C1 的直接影响

| 原假设 | 现状 |
|---|---|
| 「locator 媒介能提升幻觉修正率」 | **在本数据集 + 本模型上不可检验**——修正率的天花板是 100%，两臂都顶着天花板 |

**但这不等于 C1 被证伪**。正确读法是：

> 当**基座模型自身足够准确**时，反馈媒介的形态不产生可测差异；
> 该机制的价值只可能在**基座模型会犯错的条件下**显现。

这句话本身就是一条有价值的实证发现，且直接给出下一步实验设计。

### 12.4 另一个被这次实验意外暴露的事实

基线评测里还有两个数字，比修正率更值得注意：

| 指标 | 值 | 含义 |
|---|---|---|
| `needs_confirmation_rate` | **0.9375** | 240 单里 225 单被判「需人工确认」 |
| `confirmation_accuracy` | **0.3625** | 而人工确认的判断只有 36% 正确 |
| `business_decision_accuracy` | **0.35** | 业务决策正确率 35% |
| `error_auto_release_rate` | **0.0167** | 错误自动放行率 1.67%（4/240） |

> **系统的瓶颈不在「抽取准确率」，而在「要不要放行」这个决策层。**
> 抽取已经接近满分，但 93.75% 的订单要人工看，且这个判断只有 36% 正确。
> 这对论文的启示是：**C1 的落点或许应该从「修正幻觉」移到「可核查的证据如何支撑放行决策」**。

### 12.5 修复方案：模型能力阶梯（D20）

既然差异只可能在「基座模型会犯错」时出现，就把模型能力作为**自变量**：

| 档 | 候选模型 | 探测结果 |
|---|---|---|
| 弱 | `qwen3-8b` | ⏳ 见 §12.7 |
| 中 | `qwen3.5-flash` | **10/10 全对 → 仍饱和** |
| 强 | `qwen3.7-plus`（当前） | 已饱和（20/20） |

**为什么这比单点对照更强**：论文可以给出「**locator 的收益随基座模型能力下降而单调上升**」
的剂量-反应曲线。这既是更强的实证主张，也把「locator 无用」的负面结果**转化为机制适用
边界的正面刻画**——审稿人通常更认可后者。

**成本**：弱模型单价远低于 `qwen3.7-plus`，且延迟更低。20 次调用约 ¥0（免费额度内）。

> ⚠️ **需要同时确认的事**：弱模型能否产出结构合法的 `ParsedOrder`。若弱模型直接解析失败
> （`error_rate` 高），说明它撑不起这条流水线，需换中间档而非最弱档。

### 12.6 中间档探测：`qwen3.5-flash` 同样饱和

```
qwen3.5-flash × subtle × 5 样本 × 2 臂 = 10 次调用
→ 10/10 corrected → NO_GO（Δ = 0，p = 1.0）
```

产物：`evaluation/results/novelty_experiment_subtle_20261002_014639/`

**中档模型也 100% 修正**。这进一步支持 §12.2 的判断：问题不在模型能力档位，
而在**任务本身太容易**——只要模型能重读一遍原表，它就能改对。

### 12.8 能力阶梯探测：三个档位全部饱和（决定性）

对三档模型各跑 `subtle` × 5 样本 × 2 臂：

| 模型 | 档 | A（自然语言） | B（locator） | Δ | 判定 |
|---|---|---|---|---|---|
| `qwen3.7-plus` | 强 | **1.00** | **1.00** | +0.0000 | NO_GO |
| `qwen3.5-flash` | 中 | **1.00** | **1.00** | +0.0000 | NO_GO |
| `qwen3-8b` | 弱 | **1.00** | **0.80** | **−0.2000** | NO_GO |

产物：`novelty_experiment_subtle_20261002_013056/`、`..._014639/`、`..._015305/`

**读法**：

1. **自然语言臂在三个能力档位上都是 100%**——从最强的 `qwen3.7-plus` 到最弱的
   `qwen3-8b`，措辞反馈从未失败过。
2. **最弱档下 locator 臂反而出现 1 次 `error`**（不是修正差异，是解析失败），
   Δ = −0.20。差异不显著（p = 1.0），但**方向上没有任何支持 C1 的证据**。
3. 合计 **50 次调用**（含前面两档），**0 个「A 错 B 对」的 discordant pair**。

> **G0 门禁判定：C1 的实证主张在本数据集上不成立，且不是靠调难度或换模型能救的。**

### 12.9 为什么换模型也救不了

因为问题不在「模型不够弱」，而在**任务的性质**：

- 自建数据集是**程序生成的干净 Excel/文本型 PDF**，表格结构规整、无 OCR 噪声；
- 抽取任务本身对现代 LLM 是**简单模式匹配**——重读一遍就能改对；
- 因此**反馈媒介的形态不可能产生差异**：无论你告诉它「第 6 项数量不对」还是
  「第 17 行第 5 列原文是 100」，模型都会去重读那一行，然后答对。

> 用 §11.4 的话说：**天花板是任务给的，不是模型给的。**

### 12.10 那么 C1 还剩什么

**被证伪的是「能提升修正率」这个实证主张，不是「定位符可核查」这个形式化主张。**

| 主张 | 状态 |
|---|---|
| ~~C1a：locator 媒介能提升幻觉修正率~~ | ❌ **实证不支持**（50 次调用，0 个正向 discordant pair） |
| **C1b：locator 使每条主张成为可被第三方机器核查的对象** | ✅ **形式化成立**，不依赖修正率实验（见 `11_PROBLEM_FORMULATION.md` Proposition 1） |
| **C2：验证者是纯函数，构造上不可被说服** | ✅ 可执行断言守卫（`tests/test_ablation_invariance.py`） |
| **C3：预算熔断在耗尽时升级人工而非静默放行** | ✅ 压力测试可验 |

**论文的可选出路**（需要你拍板，见 §12.11）：

| 方案 | 做法 | 代价 |
|---|---|---|
| **α. 降级 C1 为形式化主张** | 删掉「提升修正率」，改以「可核查性 / 可审计性」立论；实证部分改用 run manifest + V1–V7 断言 | 改 §3/§4/§5，工作量中等；贡献从 3 条正式降为 2 条 |
| **β. 换更硬的任务** | 用有真实错误的场景（OCR 噪声 / 扫描件 / 手写）；需先证明该场景下模型真的会错 | ❌ **PDF 已探测：同样 1.0000**（820 字段 0 错）。要制造错误必须引入 OCR/扫描噪声，需新数据 |
| **γ. 换因变量** | 不测「修正率」，改测**核查成本**（需重读多少单元格）/ **审计可复现性** | 需新指标实现；但不受天花板影响 |
| **δ. 转向决策层** | 论文落点改为「93.75% 需人工确认 vs 36.25% 判断正确」这个真实瓶颈 | 等于换一个研究问题，需重写 |

### 12.7 一个被探测暴露的移植性缺陷（已修）

第一次跑 `qwen3-8b` 时 **10/10 全部 `error`**，看上去像「弱模型撑不起流水线」。
但读错误信息发现根因是**配置**：

```
400 InvalidParameter: Range of max_tokens should be [1, 8192]
```

`application/agents/extractor.py:31` 把 `EXTRACTION_MAX_TOKENS` **硬编码为 16384**，
而 `qwen3-8b` 的接口上限是 8192。

> **这是一个真实的移植性缺陷**：系统无法使用任何 `max_tokens` 上限低于 16384 的模型，
> 且失败表现为「该模型 100% 报错」，极易被误判成模型能力问题。

**修复方式（有意不改进生产代码）**：新增**实验专用**旋钮
`--max-output-tokens`（`scripts/novelty_experiment.py::apply_output_token_budget`），
把两个上限下调为 `min(生产默认, 指定值)`，并把生效值写入 run manifest。

> **为什么不直接改 `extractor.py`**：生产代码属于冻结基线 `paper-v1-baseline`
> （`a596bd6`），实验期修改会让整篇论文的可复现性主张失效。
> 该缺陷应作为**已知限制**记入论文，并在后续版本修复。

> 这样总成本仍是 ¥0，但把「3.7 小时换一个不可解释的结果」变成
> 「3.7 小时换一个可解释、可写进论文的趋势结论」。
