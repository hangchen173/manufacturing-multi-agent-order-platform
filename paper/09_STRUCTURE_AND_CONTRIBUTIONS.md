## 2. 核心贡献（3 条正式 + 1 条附带）

### C1｜证据锚定的对抗验证协议（VEAP）

**一句话**：把多智能体辩论的**媒介**从自然语言论证换成**机器可核查的证据三元组** `E = (kind, locator, value)`。

三个可检验的设计约束（每一条都在代码里有对应实现）：

| 约束 | 内容 | 代码位置 |
|---|---|---|
| **反证必须可复现** | 验证者的 CHALLENGE 必须携带 `locator` + 原文真实值，否则不予采信 | `application/protocol/adversarial.py: challenge_evidence()` |
| **反馈剔除措辞** | 回灌给生产者的反馈**只含 locator 与原文值，不含验证者的自然语言理由** | `adversarial.py: build_counter_evidence_feedback(mode="locator")` |
| **无证据不放行** | 无可复现证据的字段一律不得进入自动通过 | `application/blackboard/` + `grounding_verifier.py` |

> ⚠️ **注意第三条的实现现状**：目前「无证据不放行」是通过「挑战未解决 → 标记 disputed → 交人工」间接实现的，**不是一条独立的硬门禁**。写论文时要么补上这条硬门禁，要么把措辞改成「争议字段不得进入自动通过」（后者与代码一致）。**这一条必须核对后再写。**

### C2｜可核查性的实证刻画（核查成本 + 审计可复现性）★ **全文最硬的一块**

> ⚠️ **2026-10-02 重大修订（D20）**：原 C2 主张「locator 媒介能提升幻觉修正率」，
> 已被 **G0 门禁证伪**——两档注入难度 × 三档模型能力、**共 50 次调用，
> 0 个「A 错 B 对」的 discordant pair**，全部饱和。根因：任务本身太容易
> （基线抽取准确率 0.998+，全库 29,410 字段仅 57 错），模型重读即对。
> 详见 `06_NOVELTY_EXPERIMENT.md` §12。
>
> **处置（α + γ）**：保留 C1 的形式化主张，**把因变量从「修正率」换成两个
> 不受模型能力影响的确定性指标**。

**一句话**：量化「把反证媒介从自然语言论证换成机器可核查的定位符」在
**核查成本**与**审计可复现性**两个维度上的代价与收益。

| 子项 | 因变量 | 为什么不受天花板影响 |
|---|---|---|
| **C2a 核查成本** | 验证一条主张需要比对的**单元格数** | 纯组合量：locator 体制 = **1 格/条证据**（$\rho(\ell,D)$ 直接寻址）；自然语言体制 = 需扫描**整个区域** $\lvert D \rvert$ 格 |
| **C2b 审计可复现性** | 仅凭持久化证据、**不调用任何模型**即可复现的历史驳回比例 | 验证者是确定性纯函数（C1 的纯函数性），复现与否与模型能力无关 |

| 项 | 内容 |
|---|---|
| 设计 | **确定性度量**，零 LLM 调用；两体制在同一批订单上对比 |
| 样本 | 240 个测试订单（`orders/test/`）+ 423 条历史运行产物 |
| 主指标 | C2a：每条主张的单元格比对数<br>C2b：审计可复现性、证据解析成功率 $\rho(\ell,D)=v$ |
| 成本 | **¥0**（不调用模型） |
| **实测（2026-10-02 已完成）** | **C2a：292.1 : 1**（区域均值 292.1 格 vs locator 1 格）<br>**C2b：0.0000**（423 条记录 0 条带证据链；1,676 条问题 0 条带定位符）<br>**附带：定位符解析率 23,528/23,528 = 1.0000**（补上 D16） |
| 现状 | ✅ **跑完，零成本**。见 `13_VERIFIABILITY_EXPERIMENTS.md` |

**为什么这块仍然硬**：它把「定位符比自然语言论证更好」从一句**无法证伪的直觉**
变成一条**可测的、有明确数值的**主张，并且**如实报告了原假设的失败**——
审稿人通常更认可「作者知道自己的机制在什么条件下才有价值」。

> **诚实性要求**：论文必须**同时**报告 G0 的负面结果与 C2 的正面结果。
> 只报后者会被视为选择性报告。正确写法是：把 G0 作为**机制适用边界**的刻画——
> 「当基座模型自身足够准确时，反馈媒介形态不产生可测差异（§12 实证）；
> 该机制的收益体现在**核查与审计阶段**（C2）。」

### C3｜预算感知的验证策略

**一句话**：在统一的三重预算（token / 调用次数 / 墙钟）下给出 accuracy–cost 的 Pareto 前沿，并确立「**预算耗尽时升级人工，而不是降低标准**」的策略及其代价。

| 项 | 内容 |
|---|---|
| 预算定义 | `application/protocol/budget.py`：`max_tokens=200k` / `max_llm_calls=12` / `max_wall_ms=300s` |
| 熔断行为 | 超限抛 `BudgetExhausted` → `ESCALATE` 转人工（**不静默通过**） |
| 相对优势 | **多数同类工作（含 MAD、MoA）不报告计算预算**，无法判断增益是否来自「单纯多花了算力」 |
| 呼应 | ACL 2026 的 compute-efficiency 评估框架 |

## 5. 一个必须在写作前解决的叙事问题 ⚠️

**已实测数据暴露出的问题**：

`evaluation/results/baseline_generated_complex_test_20260910_234250/summary.json`（240 样本）：

| 指标 | 实测值 |
|---|---|
| 订单级字段准确率（order_number / customer_name / total_amount） | **100%** |
| 需要人工确认的订单比例 | **93.75%**（225 / 240） |
| → 即**自动通过率仅 6.25%** | |

**这会招致审稿人的直接质疑**：「既然 94% 的单子都要人工看，你这套自动化的价值在哪？」

**两个应对方向**（必须选一个，并据此重跑或补测）：

| 方向 | 做法 | 代价 |
|---|---|---|
| **A. 补测字段级自动通过率** | 订单被升级是因为**任一字段**有争议；字段级通过率可能远高于 6.25%。补测后把叙事从「订单级」改为「**字段级**」——「让 90%+ 的字段免于人工，只把有争议的字段推给人」 | 低（改评测聚合口径，不需重跑模型） |
| **B. 把保守性作为卖点** | 论证「高升级率正是证据锚定的代价，换来的是 0 逃逸」——但需要证明**基线在同等升级率下逃逸更多** | 中（需要在统一人工介入率下重跑基线） |

> **建议选 A**：它更可能给出好看的数字，且不需要重跑模型。
> **这是一项新增行动项**，已记入 `08_SUBMISSION_PLAN.md` 阶段 3。
